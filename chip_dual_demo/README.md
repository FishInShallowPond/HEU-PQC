# LC01 双芯片密码通信演示 v3.2

独立的 Windows 桌面演示程序。两块芯片各连接电脑的一路串口，由电脑转发必要数据。沿用原算法测试程序的宏命令，不需要修改芯片固件。

当前程序在同一主窗口提供两个独立模式：

- **算法演示**：保留原13种算法配置、单步/一键执行、K1/K2比较、验签结果、篡改编辑、原始TX/RX和记录导出。
- **文本加密通信**：采用类似即时通信软件的单一聊天时间线，支持A/B双向文本、图片选择、Ctrl+V粘贴图片、缩略图查看、另存和完整下载。会话建立前由芯片1生成签名密钥并签名、芯片2实际验签，随后执行KEM、KEM签名绑定和双向密钥确认。没有单步模式，也不直接比较K1/K2。

仍由一台Windows电脑连接两块板，业务报文只在电脑内存中转交；双电脑TCP后置。

主窗口仅显示“算法演示”和“文本加密通信”两个固定尺寸模式按钮，当前模式以颜色区分，切换时不改变窗口或按钮大小；界面不显示版本号。

## 文本与图片通信操作

通信页拥有自己的签名/KEM算法、两路串口、波特率和命令超时设置，并可独立点击“刷新串口”选择设备，不需要切回演示页。

1. 在通信页独立选择签名算法、KEM算法、两路串口、波特率和命令超时；用“刷新串口”选择当前设备，无硬件时勾选流程模拟。
2. 点击“连接”。芯片1生成本次会话签名密钥并签名，芯片2写入对应公钥并实际验签。
3. 验签通过后切换KEM配置：芯片1 KeyGen → 芯片2用公钥封装 → 芯片1用私钥解封装。随后切回签名配置，芯片1签名本次PK/CT和挑战，芯片2再次验签。
4. 两端分别用芯片K派生业务密钥，通过双向HMAC密钥确认；确认通过后才启用文本和图片收发。
5. 聊天框在会话主体上方，输入框固定在聊天框下方。选择或粘贴图片后先显示附件预览，点击发送才进行认证加密传输。
6. 图片发送完成后，聊天中显示缩略图、文件名、尺寸、大小和SHA-256验证状态；“查看”打开大图，“下载”另存到指定目录。
7. 回复图片可先复制到剪贴板，再在输入框按Ctrl+V粘贴。也提供“图片”按钮从文件选择。
8. 右侧栏可拖动分隔线调整宽度，也可用“隐藏侧栏/显示侧栏”整体收起。侧栏中的“会话密钥”页显示K(A端)、K(B端)、A→B和B→A的AES-256-GCM密钥；默认只显示掩码和指纹，勾选“显示完整密钥”后可查看或复制。
9. 侧栏中的“密文/报文”页显示所选消息的Nonce、AAD/报文头、密文、认证标签和完整报文HEX；图片文件可按“文件开始、数据块、文件结束”逐条切换查看。点击消息下方“报文”会自动打开对应页。
10. “清空聊天”只清除当前聊天窗口中的可见消息和临时附件，底层加密审计记录仍会保留并可导出。
11. 点击“重新建钥”会重新进行签名KeyGen/验签和芯片KEM KeyGen/Encaps/Decaps。旧密钥立即关闭，聊天与图片历史保留，新一轮序号从0开始。

签名公钥只用于本次通信会话，不创建或保存身份资料。这能验证芯片1对本次握手和KEM数据的签名以及芯片2的实际验签，但不等同于跨会话的长期可信身份、证书体系或防复制硬件身份。

密钥面板中的“指纹”是密钥原始字节的SHA-256摘要，以64位大写HEX显示，例如 `K(A端)` 下方就是 `SHA-256(bytes(K_A))`。它用于核对两端是否得到同一份密钥，不能还原密钥，也不代替完整密钥展示。K(A端)、K(B端)以及两把方向不同的AES密钥分别计算指纹；掩码默认只显示完整密钥HEX的首尾各8个字符。

两个方向使用独立的AES-256-GCM密钥及nonce前缀；报文头整体纳入AAD，并严格检查会话、方向、序号和长度。每条最多65536 UTF-8字节，每方向最多2^20条且累计明文不超过64MiB。达到限额后应重新建立共享密钥。

图片保留原始文件字节，不做重编码；单文件上限16MiB、最大32兆像素，支持PNG、JPEG和WebP，动画图片不支持。接收端只在全部文件块认证成功、结束记录完整且SHA-256一致后保存和生成预览。

**签名验签和认证加密不等于经过独立安全证明的通用安全协议。** 勾选“流程模拟”时，签名与KEM响应来自哈希协议替身，不能据此验证PQC算法或真实硬件。固件是否支持不复位连续切换签名/KEM配置并重新装载用途密钥，仍需现场验证。完整协议边界见[v3.2设计](docs/v3.2-design.md)。

## 启动

如果使用已打包版本，直接双击 `bin/LC01_DualChip_Demo_v3.2.exe`，无需安装 Python。历史版本EXE保留在同一目录；其中 `bin/LC01_DualChip_Demo_v3.1.exe` 已恢复到与历史发布SHA-256完全一致的版本，并单独完成冒烟验证，来源与校验值见[v3.1恢复说明](docs/v3.1-restoration.md)。

环境：Python 3.10 或更高版本（包含 Tkinter）；真实硬件需要`pyserial`；认证加密使用`cryptography`；图片校验、缩略图和剪贴板粘贴使用`Pillow`。

在本目录打开终端，首次安装依赖：

```powershell
python -m pip install -r requirements.txt
python main.py
```

也可以双击本目录的 `启动演示.cmd`。无硬件时可勾选界面的“流程模拟”，或者使用：

```powershell
python main.py --simulate
```

界面预览见 `docs/preview_v3.2.png`（聊天与图片）、`docs/preview_v3.2_packet.png`（逐块报文明细）、`docs/preview_demo.png`（算法演示），以及v2篡改窗口 `docs/preview_tamper_editor.png`。Pillow现在用于图片校验、缩略图和Ctrl+V剪贴板粘贴；`--screenshot PATH` 也使用它。

模拟模式使用哈希构造的协议替身，只用于演示窗口、数据转发和流程，**不实现 Kyber/Dilithium/Aigis，不能作为芯片或密码算法正确性的证据**。真实硬件模式不会自动回退到模拟。

## 连接与操作

1. 两块芯片分别连接电脑，例如芯片1为 `COM5`，芯片2为 `COM6`。两块芯片的电源、时钟和接线沿用原算法测试环境；无需把两块芯片的 UART 直接互连。
2. 关闭占用这两路串口的其他工具，手动复位两块芯片。
3. 选择相同的算法配置，填写两路串口。默认波特率 `38580`，串口读取超时 `0.2s`，命令超时 `20s`，命令间隔 `0.08s`，与原测试的波特率保持一致；命令超时留出长字段传输时间。
4. 连接并初始化后，使用“单步”逐步讲解，或者“一键执行”完成流程。也可直接一键开始。
5. 界面显示各阶段状态和实际字段，KEM 对比 K1/K2，签名显示芯片2返回的验签结果。停止请求在当前步骤完成后生效，随后可以继续。
6. 使用“导出”保存当前记录，包括尚未完成或出错的会话。需要换算法或重跑时，先断开，再复位芯片并开始新会话。

通信错误会终止流程并关闭串口，保留已得到的字段和日志。K 不一致、芯片返回验签失败均按实际值显示，不修改为通过。

## 篡改与错误演示

勾选“发送前暂停 / 篡改演示”，再执行“一键运行”：

- KEM 会先在公钥发送前暂停；继续后，芯片2完成封装，再在密文发送前暂停。
- 签名流程会在芯片1生成签名后、向芯片2发送数据前暂停。
- 点击“篡改 / 对比”，选择公钥、密文、签名或消息。左侧保留正常字节序的原始值，右侧编辑待发送副本。可以手动修改等长 HEX，或指定从0开始的字节偏移和 XOR 掩码进行翻转；掩码 `01` 表示翻转该字节最低位。
- 确认应用后继续执行；也可以恢复原始数据。编辑本身不会发送串口命令，已发出的数据只能查看，不能重写历史。
- 两颗芯片的数据页签默认比较原始输出与对端输入，并逐字节标红差异。共享密钥 K1/K2 也会标红不一致的字节。颜色仅用于标注，不阻止后续计算。

例如，芯片2封装后把正常序 CT 的第0字节异或 `01`，再继续：芯片1接收到修改后的 CT，并使用自己的 SK 进行解封装，随后显示实际 K1/K2 比较结果。签名可按同样方法修改，再由芯片2对实际收到的签名验签。**不预设硬件必然返回什么结果，不伪造 K 或验签状态。** 若芯片拒绝命令或发生超时/协议错误，会保留日志并明确报错，不将通信故障冒充为“正确拒绝篡改”。

接收/输入页签显示上位机实际下发且已获有效响应的数据：芯片2的公钥输入、芯片1的密文输入、芯片2的消息与签名输入。它们与芯片生成的原始输出分开保存；**这些输入记录不是芯片寄存器读回值**。

## 算法演示页的两种流程

**密钥封装（Kyber / Aigis-ENC）**

```text
芯片1：KeyGen → PK、SK
                  PK ──电脑原样转发──→ 芯片2：Encaps → CT、K2
芯片1：Decaps(SK, CT) ←──电脑原样转发── CT
                 ↓
                K1 ──与K2逐字节比较
```

**数字签名（Dilithium / Aigis-SIG）**

```text
芯片1：KeyGen → PK、SK → Sign(SK, M) → Signature
                  PK、M、Signature ──电脑转发──→ 芯片2：Verify
```

私钥只在芯片1读取、展示和装载，不发送给芯片2。签名与解封装前，沿用原测试流程向芯片1装载同一份私钥。

## 数据与字节序

- 界面的公钥、私钥、密文、共享密钥和签名均为**正常/软件字节顺序的完整 HEX**，可以复制。正常字节序的转换与原 `formats.py` 一致：对每个完整串口字段逐字节反转。例如芯片返回 `01 23 AB CD`，界面显示 `CDAB2301`。
- 封装响应先按通信长度切分 `CT` 和 `K`，再分别反转显示，不能对两者拼接后整体反转。
- 未篡改时，芯片之间传递的公钥、密文、签名保持原始字节；篡改时，正常序编辑副本转换回串口字节序后下发。串口头和长度字段不属于算法数据，不能在字段编辑器里修改。
- 签名消息按输入的 UTF-8 或 HEX 正常顺序显示；实际发送时沿用原程序的“完整消息反转 + 总计7字节前后补零”规则。默认签名和验签使用同一消息；主动篡改消息时，两份消息分别记录。
- 当前接口限制签名消息为 **1～1000字节且长度不是8的倍数**。中文 UTF-8 按编码后的字节数计算；不符合时明确提示，不自动修改消息。

## 算法与通信长度

配置命令和通信长度取自相邻工程 `HEU_py_acvp_pqc_main_v1/config.py`、`device/chip_client.py`，也与既有功耗测试使用的线长度相符。

| 配置 | 配置命令 | PK / SK / CT / K（字节） |
| --- | --- | --- |
| Kyber512 / 768 / 1024 | `020001000011` / `12` / `13` | 800 / 1632 / 768 / 32 |
| Aigis-ENC I / II / III | `020001000051` / `52` / `53` | 800 / 1632 / 768 / 32 |

| 配置 | 配置命令 | PK / SK / 签名（字节） |
| --- | --- | --- |
| Dilithium 2 | `020001000071` | 1312 / 2528 / 2420 |
| Dilithium 3 | `020001000072` | 1952 / 4000 / 3293 |
| Dilithium 5 | `020001000073` | 2592 / 4864 / 4595 |
| Aigis-SIG I | `020001000091` | 1312 / 2528 / 2420 |
| Aigis-SIG II | `020001000092` | 1952 / 4000 / 3293 |
| Aigis-SIG II-B | `020001000093` | 1952 / 4000 / 3293 |
| Aigis-SIG III | `020001000094` | 2592 / 4864 / 4595 |

**这些是既有芯片接口的通信长度，不代表各标准参数集的完整长度。** 新程序不使用软件随机补齐、不截断芯片结果。若实际固件返回长度与表中不符，会明确报错并保留实际响应；应据现场固件协议修正 `profiles.py` 后重试。

验签响应 `00` 为通过、`01` 为失败；其他响应作为协议错误处理。命令响应严格校验类型、长度和读取完整性，解封装只接受完整32字节 K，不从多余数据中截取。

## 日志与导出

日志实时显示在窗口；通过 Python 或启动脚本运行时，也会打印到启动终端。打包的窗口程序通过界面查看和导出日志。导出选择的目录内会新建独立时间戳目录：

- `fields.txt`：可直接阅读和复制的完整正常序 HEX，含字段字节数。
- `result.json`：硬件/模拟模式、配置、完成步骤数、最终结果及完整正常序字段。
- `command_trace.json`：每条命令所属芯片、完整原始 `tx_hex` / `rx_hex`、计划发送的 `attempted_tx_hex`、耗时、成功状态和错误原因。若发送前发现残留告警，则不发送新命令，记录的 `tx_hex` 为空；若系统写入异常，已实际写出的字节数可能无法确定，结合错误与计划命令排查。
- `session.log`：步骤和串口命令日志。
- `text_sessions.json`：算法演示主会话的历史兼容字段；v3.2聊天使用独立的`communication.json`。

最终结果为 `null` 表示尚未得到比较/验签结论；`false` 表示已经取得真实的失败结果。通信错误另外记录在 `communication_error` 字段中。

故障演示还导出 `transfers`（原始值、待发值、实发值、端点和从0开始的差异字节偏移）、`comparisons`、`edit_history` 与 `tampered`。`delivered=true` 表示相应数据已下发并获得有效响应，`read_back=false` 明确其不是硬件读回。

发送与响应确认分开记录：即使完整命令发送后接收超时，`sent_hex` 仍保留已提交给串口的字段，`delivered` 仍为 `false`。`send_status` 为 `complete`（系统串口写入完整）、`partial`（系统报告仅写入部分）、`not_sent`（未写入）或 `unknown`（写入异常，实际数量无法确认）；完整原始/计划命令分别保留在 `tx_command_hex` / `attempted_command_hex`。系统写入成功不等于对端已经收到。

## 代码

`profiles.py` 算法配置；`protocol.py` 串口、宏命令及配置切换；`workflow.py` 算法演示双芯片流程与记录；`simulation.py` 明确隔离的协议模拟；`gui.py` 同窗口双模式主界面；`communication.py` 芯片1签名验签、KEM绑定及重建密钥状态机；`communication_panel.py` 聊天、图片和独立串口界面；`image_utils.py` 图片校验、缩略图与剪贴板读取；`text_crypto.py` 通用认证加密记录层；`main.py` 入口。所有文件自包含，不依赖相邻算法测试工程或厂商 DLL。

通信模式不写入任何签名密钥文件。签名公私钥随芯片配置切换在本次Python会话内存中重新装入，重新建钥时重新生成；程序不提供跨会话恢复。通信导出包含`communication.json`和脱敏后的`command_trace.json`；私钥和共享密钥的串口内容只记录字节数并标为redacted。v2演示导出的完整芯片记录保持原语义。
