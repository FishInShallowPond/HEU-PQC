# v3.1 双模式与芯片1签名交付验证 — 2026-11-03

同一主窗口提供“算法演示”和“文本加密通信”两种模式。通信模式由芯片1生成当前会话签名密钥并签名，芯片2使用对应公钥实际验签；随后执行KEM、芯片1签名绑定KEM、双向密钥确认和文本对话。不创建或保存身份/签名密钥文件。

## 自动验证

- `python -m unittest discover -s tests -v`：**80/80通过**，退出码0。完整输出见[test-results-v3.1.txt](test-results-v3.1.txt)。
- 全部7种签名配置和6种KEM配置均走完模拟芯片配置切换、芯片1签名/芯片2验签、KeyGen、封装、解封装、KEM签名绑定和文本发送；原13种v2配置回归继续通过。
- 每个新通信会话重新生成芯片1签名密钥；重新建钥再次签名验签并生成新KEM公私钥、密文和会话编号。旧文本密钥立即关闭，聊天历史保留。
- 有效验签拒绝在KEM前阻止通信；未知返回码作为通信错误；KEM后的签名绑定被拒时不发布文本密钥；错误K只导致双向密钥确认失败，不复制或直接比较K值。
- 密文、tag、AAD头篡改及重放不交付明文。通信导出保留公开签名、PK/CT、有效响应、完整报文和拒绝原因；SK/K命令只记录字节数并标记redacted。
- 实际Tk测试验证两个模式按钮固定尺寸、当前模式仅改变颜色、切换前后主窗口尺寸不变、界面不显示版本号。
- 通信页有独立签名/KEM算法、芯片1/2串口、波特率、命令超时和“刷新串口”；测试确认刷新只更新通信页选择项，不修改演示页端口变量。
- 最小1120×780尺寸下所有模式、串口刷新、连接、重建、结束、导出、A/B收发、故障和报文详情控件可见。
- `ruff check --select F,E9`和Python编译检查通过。

## 证据边界

- 测试没有打开真实COM端口。PQC签名和KEM响应来自明确标识的哈希协议替身；真实双板签名、验签、算法配置连续切换、KeyGen/Encaps/Decaps及重新建钥仍需现场验收。
- 芯片1本次签名公钥由同一握手交给芯片2，用于演示芯片1签名、芯片2验签和本次KEM绑定。该公钥没有跨会话预置信任，不能称为长期可信身份或防复制硬件身份。
- 本版不包含双电脑TCP、证书/PKI、图片/音频、MCU或QKD。HKDF/HMAC/AES-GCM使用真实软件库，但不证明PQC算法和芯片硬件正确。
- 演示协议不是TLS，也没有经过独立密码协议安全证明。
