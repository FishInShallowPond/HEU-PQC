# v0 验证记录

日期：2026-11-04。该文件在交付打包前补齐实际执行结果；未列为通过的内容不得按已验证处理。

## 环境和证据

- Windows x64，MSYS2 UCRT64，GCC 15.2.0，OpenSSL 3.6.2；C99。
- 自动化日志在开发构建时写入项目临时目录；交付前清理，不进入最终 ZIP。
- 软件验证后端采用真实 ML-DSA-44 / ML-KEM-512，各端独立生成私钥；没有软件hash替身或随机补齐。
- 测试端的自动指纹确认仅存在于测试入口。正常 GUI 需要双方核对并分别确认。

## 已完成的核心验证（2026-11-04 最终构建）

- `test_crypto`：436项检查，0失败。包含SHA-256、HMAC、RFC5869 HKDF、AES-256-GCM已知答案，认证失败输出清零、33B消息精确签名和独立EVP验证、KEM封装解封装及错误参数。
- `test_chip`：56项检查，覆盖帧长、ACK、告警、消息反转及填充、无效串口参数；不打开物理串口。
- `test_chip_serial`：115项检查，Win32串口API测试替身执行真实驱动状态机，核对配置切换与SK重装、PK/SIG/CT/K逐字段顺序、分片响应、短写、取消、告警、未知返回码和接收缓冲边界；不是板卡算法验证。
- `test_session`：通过。覆盖双向方向密钥、未确认拒绝发送、认证记录、重放、方向/session/seq/长度/密文/tag/截断拒绝与key用量限制。
- 确认顺序回归：先复现“B未校验即回复有效确认”，修复后对FINISH/ACCEPT、双方角色分别注入0/31/错误32B；共12个拒绝组合、4个成功组合及失败会话清理验证。B只在成功验证后返回凭据。
- 独立双进程：正常文本/ACK、双向12425B多块文件与SHA-256一致、第二次握手指纹改变、换钥后双向文本；签名、FINISH、ACCEPT、业务密文、CT、模式六类故障按指定阶段拒绝。两端各自进程，不在网络直接比较K。
- 原生窗口联调：两个独立EXE窗口在软件PQC模式完成双方指纹相等、双向文本及ACK；B发起换钥后两端指纹改变并重新确认，随后文本继续送达。测试端通过独立的Win32自动测试脚本完成，该临时脚本和测试截图不在交付目录中。
- 独立审查后的修正：ACK 只从发送 `FILE_END` 后开始计时；换钥/断线清空旧会话命令；未完成文件写入隐藏 staging，启动时清理可删除的崩溃遗留；窗口关闭会等待工作线程真正退出；远端文本转义换行、控制符和双向控制符；运行后端在标题栏和日志中显式标识；运行中锁定接收目录；端口/波特率在窄化前严格解析。
- 发布EXE：`--self-test`和`--gui-smoke`退出码均为0。EXE SHA-256：`2AB09DEB41684BB1DBF3E3391C42424A4EA6CEBFF990E6C322C5729699682082`。

## 资源观察的适用范围

GCC Release的`-fstack-usage`静态单函数报告：`lc_handshake`约10128B，固定profile串口`hw_command`约8400B。这些是Windows目标的单函数帧，不能相加以外地误作整个系统峰值，也不等于MCU测量；必须进一步统计嵌套调用、密码库、线程、DMA和业务队列。业务块上限4096B、文件上限16MiB，采用流式IO。

- 固件原始Dilithium2/Kyber512是否与所称参数和接口完全一致；不能据软件标准算法通过来认定。
- MCU移植、MCU直接控制LC01、目标RAM/Flash/吞吐/延迟和功耗。
- 商用品对标、密码协议第三方安全审计、长期设备身份/证书管理。
- QKD设备、光链路、供钥服务与混合供钥均未实现/验证。
